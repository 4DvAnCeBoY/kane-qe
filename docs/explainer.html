kane-qe v2, explained simply

A dashboard light for your robot tester

An AI tester clicks through a website for you, and a test takes a minute or two. kane-qe v2 is a small strip above where you type that tells you, without asking, what the tester is doing right now, what just broke and why, and whether the code you just changed has been tested at all.

The cast

Who does what

you

The tester

You say what to check: “add an iPod to the cart and make sure it shows 1 item”.

Claude Code

Your assistant

The AI you chat with. It writes code, and it starts tests when you ask.

kane-cli

The robot tester

Opens a real browser, clicks like a person, checks what you asked, and keeps a diary of every step on disk.

kane-qe v2

The dashboard light

Reads that diary once a second and shows it. It never starts a test itself, and never makes anything up.

  Band-->>You: ✓ 1 passed, or ✗ and the step it failed on

The band only reads. If kane-cli did not write it down, the band does not show it.

The band

Three rows, always there

The band sits just above where you type, in every session. The little helmet on the left is kane's mascot: its eyes move while a test runs and stay still when nothing does. So a glance tells you if anything is happening.

row 1

What kane-cli is doing: idle, running one test with its time, several runs as coloured squares, or a suite as 5 of 12 tests done.

row 2

The detail: the step a test is on, or the test that just failed and where, or a warning that code changed and nobody tested it.

row 3

How much of what the product should do has been proven by a real test. Always yellow, always last.

Real runs

What the band saw while the video was recorded

Every bar is one real kane-cli run from the walkthrough video, placed where it started and stopped. Some ran alone, some at the same time, some as part of a suite. The band followed all of them by itself: nobody told it a run had started.

When two or more bars overlap, row 1 turns into squares, one per run. When they all end, it goes back to idle with how many passed and failed.

passedfailed

Minutes from the start of the recording, before waiting stretches were sped up. 7 runs: 4 passed, 3 failed. The failures are kane's own reports, shown as they came: one run started in the wrong page, and two saved tests stopped for want of a start URL (the suite ran without --url, and those tests name none).

When a test fails

It tells you what kane found, and nothing it didn't

When kane-cli's test fails, kane investigates and writes down a verdict: the reason, what kind of problem it is, how serious, and how sure it is. kane-qe shows exactly that, with the step it failed on.

It never guesses. If kane-cli did not give a reason, the pane says so. In this real case the button kane was asked to press is on the page but hidden, so the verdict is worth reading carefully: kane calls it a product defect; a person would call it a test that asked for a button users cannot see.

After a change

Did anyone test what Claude just changed?

Claude can change code in seconds. It is easy to finish without checking the result in a browser. kane-qe notices which files Claude changed (not docs, not tool folders), and when Claude finishes, it does one of three things. You choose which.

offer · the default

A reminder with a button

The band says ⚠ 1 file changed, untested. Press Test this change: you get the saved tests that already cover those files, with how they did last time, or Claude writes a new test from the change.

auto

Claude tests before it stops

When Claude tries to finish, it is asked once to test the change first. In a real try it did: it ran kane-cli and reported back. If it still finishes without a test, the band goes back to the button.

off

Quiet

Nothing. The band never mentions changes.

Any kane-cli run that starts after the last change clears the warning, whether it passes or not: the change has been looked at.

Assurance

Proven, not just planned

A requirement says what the product should do. kane-cli can turn it into use cases, design tests for each, and record which ones a real run has proven. Row 3 of the band shows that number all the time.

These are the real numbers of the demo project. Every acceptance criterion is designed and proven, so the project reads 100%. But the second use case has no test designed at all. That is why the Assurance tab shows a card per use case: a high total can still hide a gap.

Words

A tiny glossary

run
One test kane-cli carries out: an objective in plain words, or a saved test.
saved test
A test kept as a file (…_test.md) so it can be run again the same way.
suite
Several saved tests run together, a few at a time.
step
One thing the tester did: opened a page, typed, clicked, checked.
verdict
kane-cli's own explanation of a failure: why, what kind, how serious, how sure.
evidence
The pack kane-cli keeps for every run: screenshots, network, console, each step.
assurance
How much of a requirement a real test has proven.
use case
One thing a user does with the product, taken from the requirement.
band · pane
The three rows above the prompt, and the side panel that opens with /kane.
Try it

Three steps

  1. Install kane-cli and sign in: npm install -g @testmuai/kane-cli, then ! kane-cli login --oauth in Claude Code.
  2. Load the mod: claude --plugin-dir kane-qe/kane-qe from a clone of the v2 branch. The band appears.
  3. Ask Claude: “test that searching for iPod lists at least 4 products on ecommerce-playground.lambdatest.io”. Watch the band.
