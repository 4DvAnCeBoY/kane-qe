Kane Cockpit Insights

The CPO asked for more interactive graphs and more value from the Claude Code mod. I read every file your five real kane-cli runs left on disk. Each run already records a full evidence pack: per-step timings, every network request, console output, 4K screenshots and a root-cause verdict. The cockpit shows roughly a tenth of it today.

Seven views for the cockpit

Each one below is a working mock: hover or click the rows, cells and bars. The numbers come from your runs on 5 Oct. In the terminal these become a Client module, which takes mouse hover, clicks and arrow keys; VS Code and mobile get the same data as text.

1 · Run timeline

Phase 1QE · SDET

A waterfall of every step, coloured by kind, sized by time. Hover a step for its timing breakdown, click it to see the screenshot and the agent's reasoning. The failing step and kane's "relevant steps" are marked, so the eye lands on the cause.

KANE · RUN TIMELINEsearch headphones · ✗ FAILED · 115.9 s · 39.1 cr
Hover or click a step.
Why it matters
Shows at a glance where a run spends time and where it went wrong, without reading logs.
Source
evidence/…/result.yaml steps, step.json duration, run_end.verdict.relevant_steps

2 · Hidden signals

Phase 1QE · Dev · CPO

A heat strip per step: requests, failed requests and console messages. A passing test that hides HTTP errors or console errors gets a warning badge on its result and in History. Click the step 2 "failed req" cell: that is where the /undefined/ call shows up. This is value the test author didn't ask for and kane already collects.

KANE · HIDDEN SIGNALSfind feature of testmu.ai · ✓ PASSED · ⚠ 3 signals
Click a cell to list what was behind it.
Why it matters
Turns every functional run into a free health check of the page: broken APIs, blocked scripts, console noise.
Source
logs/0-network.har (_step, _failed, status), logs/0-console.ndjson (level, step)

3 · Failure verdict

Phase 1QE · Lead

Kane already classifies each failure: product bug or automation problem, category, severity and confidence. The cockpit should lead with that, then offer the next action that fits the category.

KANE · VERDICTstep 9 of 10
Agent treated an empty search as product results family automation bug category agent misstep severity minor confidence
relevant steps 3 · 7 · 9 credits on this verdict 13.82 fix use a search term the catalog stocks, and check for the no-results message first
Why it matters
Separates "the product broke" from "the test is wrong", which is the first question every failure raises.
Source
run_end.verdict, steps/*/failure.yaml triage, suggested_fix

4 · Trends and flakiness

Phase 1Lead · CPO

History becomes a chart: one bar per run, height by duration, colour by result. Click a bar to open that run. Runs of the same test that both pass and fail are flagged as flaky; failure reasons are grouped so repeat causes stand out.

KANE · HISTORYlast 5 runs · 3 passed · 2 failed
Click a bar.
failure reasons final verification ▇▇ 1 checkpoint failed ▇▇ 1
Why it matters
Answers "is quality getting better or worse?" and "which tests can't we trust?" without a separate tool.
Source
session dirs (session.json, run_end), grouped by test_id / objective

6 · Step screenshots

Phase 2QE · Dev

Every step has a 4K screenshot, and clicks and types have an annotated one showing the element hit. Selecting a step in the timeline shows its screenshot in the pane. Steps whose screenshot is byte-identical to the previous one are flagged "page didn't change", a strong hint at a wasted or stuck step.

Terminal support varies. Pixel images draw in terminals with the kitty graphics protocol (kitty, Ghostty). Warp and iTerm get a text placeholder with an "Open screenshot" link. I haven't confirmed Warp's behaviour yet, and would test it before building.
Why it matters
"What did the agent see?" is the second question after every failure.
Source
steps/<n>/screenshot.jpg, annotated.png, element_rect

7 · Coverage and web vitals

Phase 3Lead · CPO

Requirement coverage (use-cases and acceptance criteria, designed vs proven, risk-weighted) and Core Web Vitals trends (LCP, CLS, INP, TTFB). Both are supported by kane-cli but produce no data yet: coverage needs a .context/ store from kane-cli context ingest, and vitals need objectives that ask for them. The cockpit can offer one-click setup for each.

Why it matters
Connects test runs to product requirements and performance budgets, the language a CPO reports in.
Source
kane-cli cover gaps --json, coverage/usecases.yaml, run_end.context.memory

kane-cli data issues to raise

Found while reading the runs. Each one affects what a dashboard can show reliably.

  • Credits don't reconcile within one run: session 39.10, run summary 34.98, verdict 13.82.
  • run_end.run_dir and session.json point to runs/0, which is never created.
  • Step numbers on the NDJSON stream are off by one from the step labels.
  • upload_status stays "pending" after a successful upload; total_duration_ms is always 0.
  • The HAR has no response sizes or bodies (-1), and some receive timings are negative.
  • Console capture covers the top frame only, so most runs log nothing.
  • whoami reports an expired token as "not authenticated" instead of refreshing it.
